## §주제1. 화투게임(Post #7 민화투) git 관리

### 기획서 커밋 단위

기획서는 마크다운 텍스트 파일(`game_plans/post7_game_plan.md`)이라 diff가 사람 눈에 바로 읽힌다. 이 장점을 최대한 활용한다. 커밋 1개 = 결정 1건 원칙을 적용하면 된다.

민화투처럼 복합 프로젝트는 결정 항목이 많다. 족보 점수 체계, AI 전략 선택(그리디/Expectiminimax), 배지 7종 조건, 난이도 승률 목표 — 이것들이 각각 별도 커밋이어야 한다. "기획서 업데이트"처럼 여러 결정을 한 커밋에 묶으면 나중에 어느 결정이 어느 시점에 왜 내려졌는지 추적이 불가능해진다.

권장 커밋 메시지 형식:
- `feat: Post7 민화투 족보 6종 점수 체계 확정 (청단/홍단/초단 +3, 고도리 +5)`
- `fix: Post7 고도리 조건 수정 — 8월 달광은 광이므로 새패에서 제외`
- `release: Post7 민화투 기획서 최종 승인 — v1.0 태그`

### 기획서 v1 → v2 → v3 진화 시 git 전략

단일 파일 누적 방식을 선택한다. 파일명에 버전 suffix를 붙이는 것은 CLAUDE.md에서 이미 금지된 원칙(위젯 파일 단일 정본 룰)과 동일한 이유로 기획서에도 금지한다. `post7_game_plan_v2.md`가 생기는 순간 어떤 파일이 현행 기획인지 혼란이 생긴다.

버전 이력은 git 태그로 고정한다:
- `v1.0` — lead 최초 승인본
- `v1.1` — game 구현 중 발견된 기획 오류 반영본
- `v2.0` — 실데이터 기반 대규모 개정본

난이도 밸런싱처럼 실험적 변형이 필요할 때만 `feature/post7-난이도실험` 브랜치를 짧게 열고 결론 나면 main에 병합 후 브랜치를 즉시 삭제한다.

### 기획서 변경이 game 구현 재작업을 트리거하는 관계

이것이 핵심 문제다. 기획서 변경 커밋의 메시지에 `BREAKS: BH_startWithDiff` 같은 영향 식별자를 명시하면, game 에이전트가 기획서 로그를 보고 어떤 구현이 재작업 대상인지 즉시 파악할 수 있다.

구체적 약속:
- 기획서 변경이 game 위젯 수정을 요구할 때 → 커밋 메시지 Footer에 `BREAKS: [검수 식별자]` 명시
- 기획서 변경이 game에 영향 없을 때(텍스트·다이어그램 추가 등) → Footer 없음

예시:
```
fix: Post7 족보 점수 이전 방식 수정 — 상대 감점 없이 내 가산만

기존: 족보 달성 시 상대 -3점, 내 +3점
변경: 족보 달성 시 내 +3점만 (상대 감점 제거 — 시니어 사용자 혼란 방지)

BREAKS: BH_calcJokbo
```

이렇게 하면 game 에이전트가 `git log --grep="BREAKS:" game_plans/post7_game_plan.md`로 재작업 트리거 커밋만 필터링할 수 있다.

### 핵심 결정 이력 보존 표준

족보 점수 체계, AI 난이도 파라미터, 승률 목표 같은 핵심 결정은 태그로 고정한다. 태그 메시지에 결정 근거를 1~2줄 기재한다:

```
git tag -a v1.0 -m "Post7 민화투 기획서 최초 승인. 족보 4종(홍단/초단/청단/고도리), 난이도 3단계, 배지 7종 확정."
```

## §주제2. 앞으로 게임 개발 워크플로우

### 기획 승인 커밋 = game 착수 신호

기획서 최종 승인 커밋(`release:` 접두사 + 태그 생성)이 game 에이전트의 공식 착수 신호가 되어야 한다. 현재 워크플로우는 lead가 구두로 승인을 전달하는데, git 태그가 붙은 커밋이 있으면 game 에이전트가 "이 시점의 기획서가 승인본"이라는 사실을 스스로 확인할 수 있다.

흐름:
```
game_planner: git commit -m "release: Post{N} 기획서 승인" + git tag -a vN.0
    → game 에이전트: git show vN.0:game_plans/postN_game_plan.md 로 승인본 확인 후 구현 착수
```

### 검수 식별자 추적 체계

기획서 [검수 식별자] 항목(예: `BH_startWithDiff`)은 game_planner가 기획서 작성 시 반드시 명시한다. game은 이 식별자를 두 곳에 사용한다:
1. 구현 코드 최상단 주석: `// BH_GP: post7_game_plan.md v1.0`
2. 위젯 완성 커밋 메시지: `feat: Post7 민화투 위젯 완성 [검수: BH_startWithDiff]`

이렇게 하면 나중에 `git log --grep="BH_startWithDiff"`로 기획서-위젯 간 연결을 추적할 수 있다.

### 기획-구현 불일치 발견 시 시정 책임

| 발견 시점 | 책임자 | 처리 방법 |
|---|---|---|
| game 구현 중 발견 | game | game_planner에게 이슈 전달 → game_planner가 기획서 수정 커밋 → game이 재구현 커밋 |
| qa 검수 중 발견 | qa | lead 경유 → game_planner 기획서 수정 → game 수정 구현 |
| 발행 후 실데이터 기반 | game_planner | 개정 기획서 커밋(`fix: 실데이터 기반 난이도 조정`) → game과 협의 후 위젯 패치 |

git revert는 이미 WP에 배포된 위젯 파일에는 사용하지 않는다. 기획서 로컬 파일에 한해 `git checkout v1.0 -- game_plans/post7_game_plan.md`로 이전 승인본 복원 후 재작업하는 것이 안전하다.

### 다른 에이전트에게 game_planner가 요구하는 인터페이스 약속

**game 에이전트에게:**
- 기획서 승인 태그 시점 파일(`git show vN.0:game_plans/postN_game_plan.md`)을 구현 기준으로 사용. 파일시스템 최신본 사용 금지(기획 수정 중일 수 있음).
- 구현 코드 최상단에 `// BH_GP: post{N}_game_plan.md v{N}.{M}` 주석 필수.
- 기획서와 다르게 구현해야 할 경우 커밋 전에 game_planner에게 보고.

**design / design_ui 에이전트에게:**
- 기획서 [UI 요구사항] 섹션을 읽을 때 승인 태그 기준 버전을 확인할 것. 기획서가 수정 중이라면 최신본과 승인본이 다를 수 있다.
- 카드 메타데이터 4개(data-title, data-badge, data-src, data-thumb)는 기획서에 명시된 값을 그대로 사용.

**sound 에이전트에게:**
- 기획서 [효과음 요구사항] 섹션에 명시된 이벤트 목록(족보 달성, 매칭 성공, 패배 등) 기준으로 6종 제작. 목록 외 추가 효과음은 game_planner와 협의 후 결정.

### 발행 후 실데이터 기반 기획서 개정 git 운영

체류 시간·완료율 데이터가 쌓이면 기획 개정이 필요하다. 이때 기획서 개정 커밋 메시지에 데이터 근거를 명시한다:

```
fix: Post7 쉬움 모드 AI 힌트 빈도 조정

근거: 발행 후 3주 데이터 — 쉬움 모드 완료율 42%, 목표 70% 미달.
힌트 자동 발동 조건 완화 (3턴 무매칭 → 2턴 무매칭).

BREAKS: BH_showHint
```

개정 기획서는 `v1.1`로 태그하고 game에 위젯 패치를 요청한다.

## §다른 에이전트에게 요청

**game 에이전트에게**: 구현 완료 커밋 메시지에 `[기획서: post{N}_game_plan.md v{N}.{M}]` 형식으로 어느 버전 기획서를 기준으로 만들었는지 명시해 주기를 요청한다. 기획서가 개정될 때 어떤 위젯 버전이 구버전 기획 기반인지 추적하는 데 필수다.

**design_ui 에이전트에게**: 기획서 [UI 요구사항]에 없는 컴포넌트를 추가할 경우 커밋 전 game_planner에게 확인 요청. 기획 범위 외 UI가 game 코드 구조에 영향을 줄 수 있다.
