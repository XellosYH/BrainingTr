## Q1. 위젯 파일 구조 — 1순위: **A**

**선택**: A — 단일 정본 강제 (`widgets/post{N}_widget.html`만 git 관리)

**근거**:
- 2026-05-25 v5b 베이스 선택 오류 사고의 직접적 원인이 파일명 복수 난립이었다. 이 사고가 반복되지 않으려면 정본 파일이 하나뿐인 구조가 전제조건이다.
- design_ui 의견서 §주제2에서 `_BH_common_ui.html` SSOT 제안이 있으나, 이는 공통 컴포넌트 원본 관리용이고 git 추적 대상에 포함된다. 납품용 정본 `post{N}_widget.html` 단일 원칙과 충돌하지 않는다.
- B안(2단계 분리본)은 개발 편의성이 있으나, 어느 파일이 "현행 정본"인지 판단을 다시 에이전트에게 위임하므로 동일 사고가 재발할 수 있다.

**game 영역 영향**:
- 작업 전 `git log --oneline widgets/post{N}_widget.html`으로 최신 SHA 확인 후 착수하는 절차가 단일 정본 원칙과 결합하면 베이스 선택 오류 재발 가능성이 구조적으로 차단된다.

## Q2. LFS 도입 임계값 — 1순위: **A**

**선택**: A — 포스트 50개 초과 또는 200MB 초과 시 도입

**근거**:
- design 의견서 §주제1에서 동일한 수치(포스트 50개/200MB)를 제안했다. design 관점에서 PNG 바이너리 자산이 가장 많으므로 이 에이전트의 임계값 판단이 가장 근거 있다 (design 의견서 §주제1 참조).
- sound 산출물은 JS 텍스트이므로 LFS 필요성이 없고, game 위젯은 HTML 텍스트이므로 마찬가지다.
- 현재 저장소 규모에서 도입은 오버엔지니어링이며 단순함 우선 원칙 위반이다.

**game 영역 영향**:
- game 위젯 HTML/JS는 LFS 대상이 되지 않는다. LFS 도입 후에도 game 작업 절차 변경 없음.

## Q3. pre-commit hook 작성 책임 — 1순위: **B**

**선택**: B — 단계적 도입 (먼저 BH_ prefix + style 단일행, 나머지는 학습 후 추가)

**근거**:
- game 의견서 §주제2에서 G1(BH_ prefix)·G3(style 단일행) 게이트를 이미 명시했다. 이 두 항목은 정적 grep으로 검증 가능하며 즉시 hook 등록이 가능하다.
- sound 의견서 §주제2에서 gain 값·BH_SoundMuted 누락·BH_getAC() 미경유 등 sound 전용 4항목도 정적 분석 가능하다고 명시했다. 단계적으로 추가 적용이 자연스럽다.
- A안(5종 통합 스크립트 즉시)은 현재 hook 자산이 없는 상태에서 dev에게 큰 부담을 주고, 미완성 hook이 배포되면 false positive로 작업 흐름이 막힌다.
- design_ui 의견서 §주제1에서 JS 이모지 escape 검증은 hook보다 수동 검증이 현실적이라고 명시했다. 모든 항목을 hook으로 강제하는 것은 과도하다.

**game 영역 영향**:
- 1단계(BH_ prefix + style 단일행) hook이 도입되면 game 위젯 납품 전 G1·G3 게이트가 자동화된다. G2(이모지)·G4(외부통신)·G5(면책문구)는 기존대로 납품 전 수동 확인 유지.

## Q4. 인터페이스 약속 7건 .md 일괄 반영 — 1순위: **A**

**선택**: A — 7건 모두 dev 위임으로 즉시 일괄 반영

**근거**:
- 이번 라운드테이블에서 5개 에이전트가 교차 참조로 합의한 인터페이스 약속들이다. 단계적 반영(B안)은 "1차 반영 완료 이후 2차 착수"라는 후속 작업이 남아 불완전한 상태가 지속된다.
- game 관점에서 수신 인터페이스(sound의 BH_queueSound 단일화, design의 미디어 ID 전달, game_planner의 BREAKS 표기)가 .md에 반영되지 않으면 다음 세션에서 규칙 인지 누락이 발생한다.
- sound 의견서 §주제2에서 BH_queueSound 인터페이스를 명시했고, game 의견서 §주제2에서 이를 수신 인터페이스로 확정했다. 이 약속이 .md에 없으면 규칙으로 작동하지 않는다.

**game 영역 영향**:
- game.md에 반영될 항목: sound BH_queueSound 호출 의무 + design 미디어 ID 수신 형식 + game_planner BREAKS 표기 수신 절차.

## Q5. 태그 명명 규칙 통일 — 1순위: **A**

**선택**: A — 영역별 prefix 표준 통일

**근거**:
- game 의견서 §주제1에서 마일스톤별 커밋과 deploy 태그를 제안했고, sound 의견서 §주제1에서 `sound-vX.X-postN` 태그 형식을 제안했으며, design 의견서 §주제1에서 `design-p7-v1` 형식을 제안했다. 세 에이전트 모두 영역 prefix를 쓴다는 방향이 일치한다.
- 제안된 표준 `plan-p{N}-v{X.Y}` / `design-p{N}-{자산}-v{X}` / `game-p{N}-{단계}-v{X}` / `sound-p{N}-v{X}`는 각 에이전트 제안과 정합하며 `git tag -l "game-*"`으로 영역별 필터링이 가능하다.
- B안(영역별 자유)은 현재 에이전트들이 이미 서로 다른 형식을 제안하고 있으므로 혼란을 방치한다.

**game 영역 영향**:
- game 태그 형식 확정: `game-p{N}-{단계}-v{X}` (예: `game-p7-fsm-v1`, `game-p7-wp-v1`). 단계명은 마일스톤 커밋과 일치시킨다.
