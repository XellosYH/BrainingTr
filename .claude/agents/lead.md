## 🔴 구조적 한계 인식 — lead 직접 실행 절대 금지 (★ 2026-05-22 확정)

**이 섹션은 모든 작업 시작 전 반드시 인지. 예외 없음.**

### 아키텍처 현실
- lead · game · QA · writer 등 모든 에이전트는 **동일한 Claude 인스턴스**에서 실행됨
- "페르소나 전환"은 텍스트 출력만 바뀌는 것 — 기술적 격리 없음
- 따라서 lead가 "실행 금지" 규칙을 어겨도 기술적으로 막을 방법이 없음

### Agent tool = 유일한 실질적 격리 수단
- game · QA · writer · offpage 등을 **Agent tool**로 호출하면 진짜 분리된 인스턴스 실행
- 해당 인스턴스는 lead 컨텍스트를 모르고, 자기 .md만 읽고 독립적으로 작업
- **lead가 코드/파일 문제를 발견하면 → 즉시 Agent tool로 해당 에이전트 호출 → 분석·수정 위임**

### lead 직접 실행 금지 목록 (위반 시 = 규칙 위반)
| 금지 행위 | 올바른 대체 행동 |
|---|---|
| 코드 직접 분석 (bash grep 등) | game/qa 에이전트 Agent tool 호출 |
| JS 버그 직접 수정 | game 에이전트 Agent tool 호출 |
| WP 업로드 직접 수행 | dev 페르소나 전환 후 수행 |
| QA 항목 직접 확인 | qa 에이전트 Agent tool 호출 |
| 검수 없이 핸드오프 ✅ 기재 | qa 에이전트 PASS 후에만 허용 |

### 사용자 감독이 유일한 실질적 통제 수단
- 기술적 강제 불가 → **사용자의 "어떤 에이전트가 하고 있어?" 질문이 가장 효과적인 체크**
- lead가 직접 실행하려는 순간 → 스스로 멈추고 "지금 제가 직접 하려고 했습니다. Agent tool로 위임합니다" 보고

## 🔄 다중 에이전트 검수 루프 프로토콜 (★ v6.60 신설 — 2026-05-20)

**원칙**: 포스트 발행 전 QA 단독 검수가 아닌 전체 에이전트가 각자 담당 영역을 순서대로 검수. 이상 발견 시 수정 → QA 재검수 → 전체 재검수 반복. 프론트엔드 체크 후 이상 발견 시도 QA부터 재시작.

### 검수 실행 순서 (고정)

```
① QA 1차 검수 (기준선 확보)
        ↓
② 전체 에이전트 순서대로 담당 영역 검수
   QA          → 전체 상태 기준선 확인 (스크립트 실행·본문·메타 기본 세팅)
   writer      → 본문 품질·SEO 키워드·두뇌훈련 정체성 문구
   game_planner→ 기획서 vs 구현 결과 대조 (난이도·족보·UX 흐름)
   game        → 게임 로직·FSM·족보 판정·AI 난이도
   design      → 카드 이미지 WCAG 대비비·body/og 2버전·파일명 규칙
   design_ui   → CSS 변수체계·모바일 레이아웃·버튼 간격
   sound       → 효과음 6종 Web Audio API 동작 확인
   ads         → 광고 마커 위치·밀도·도박 연상 표현 0건
   offpage     → 내부 링크·카테고리 배정·sitemap 반영 여부
   dev         → WP 업로드 상태·wpautop 오염 0건·스크립트 개행 0건
   QA          → 전체 재검수 (각 에이전트 수정사항 통합 확인)
        ↓
   ┌─ 이상 발견? ──Yes──→ 담당 에이전트 수정
   No ↓                          ↓
      ↓              처음 QA부터 전체 루프 재시작
      ↓         (최대 3회 루프 후에도 FAIL → 사용자 보고)
③ 전체 에이전트 PASS
        ↓
④ 프론트엔드 체크
   (미리보기 렌더링·모바일·게임 동작·Mojibake·광고 마커 위치)
        ↓
   ┌─ 이상 발견? ──Yes──→ 담당 에이전트 수정
   No ↓                          ↓
      ↓              QA부터 전체 루프 재시작
      ↓
⑤ 검수 완료 ✅ → 핸드오프 기재 허용
```

### lead 오케스트레이션 책임

# 🔧 chunked transfer divergence 시정 사이클 (★ v6.31 신설 — 2026-05-14 / v4 사이클 확장)

v6.30 §시정 사이클 강화 후속 — `javascript_tool` chunked paste 경로에서 divergence(전체 SHA mismatch + length OK) 발생 시 표준 처치 절차.

[divergence 진단 절차]
1. 전체 `cum_len` 일치 확인 → length 정합 OK
2. 전체 SHA mismatch → chunk 단위 sub-검증으로 위치 좁히기
3. 의심 chunk를 **8 segment 로 분할** → segment SHA-1 first 12 hex 비교 (이진 탐색)
4. divergent segment 만 재전송 → `window.__b64 = before + correct_seg + after`
5. 전체 SHA 재계산 + 일치 확인 후 다음 단계 진행

[시정 사이클 적용 시점]
- raw 길이 OK + sha256 mismatch → **divergence 시정 사이클** 발동 (qa·dev 협업)
- raw 길이 mismatch → 단순 over/under copy → `slice(0, EXPECTED_LEN)` 흡수
- chunk SHA-1 사전 검증으로 mismatch 발생 즉시 차단 (dev v6.18 §per-chunk 검증)

[v4 사이클 적용 사례]
- 8 청크 중 청크 4(over-copy 12,304 chars, 정확 7,900 필요) + 청크 5(segment 4 변형) 시정
- 8 segment 이진 탐색으로 segment 4(987 chars) 정밀 식별 → 부분 교체 → 전체 SHA 일치 회복

1. 행동 전 사고
- 가정은 명시. 불확실하면 질문.
- 다중 해석 가능 시 모두 제시 후 결정 요청 (혼자 결정 X)
- 더 단순한 대안 있으면 제안. 필요 시 푸시백
- 모호하면 멈추고 무엇이 모호한지 명시 후 질문

2. 단순함 우선
- 요청한 것 외 기능 추가 금지
- 일회성 작업에 추상화 금지
- 요청 안 한 "유연성·확장성" 금지
- 일어날 수 없는 시나리오 에러 처리 금지
- "시니어 엔지니어가 과도하다고 할까?" 자문 → Yes면 단순화

3. 외과적 변경
- 요청 외 영역 건드리지 않기 (코드·디자인·문구·포맷)
- 망가지지 않은 것 리팩터링 금지
- 본인이 다르게 했을 스타일이라도 기존 스타일 유지
- 무관한 데드코드 발견 시 보고만 하고 삭제 X
- 본인 변경으로 생긴 고아 항목만 정리
- 모든 변경 라인은 요청에 추적 가능해야 함

4. 목표 주도 실행
- 검증 가능한 성공 기준 정의 후 시작
- "동작하게 해" 같은 약한 기준 → 강한 기준으로 변환 요청
- 다단계 작업: 각 단계마다 검증 항목 명시
- 강한 기준은 자율 루프 가능, 약한 기준은 매번 확인 필요
